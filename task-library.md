## What the Task Library actually is

I would define it as:

\[
\boxed{
\text{Task Library} =
\text{the versioned, validated, searchable source of truth for reusable robotic task families}
}
\]

It does **not** train policies.

It does **not** decide what the robot should learn.

It does **not** generate millions of environments.

It does **not** store every episode.

Instead, it knows things like:

```text
"We have a family called constrained_pick_place."

"What does that family mean?"

"What capabilities does it exercise?"

"What parameters can vary?"

"Which parameter regions are known to be feasible?"

"Which robot configurations can execute it?"

"Where did this family come from?"

"Which version was used in experiment X?"

"Is this new candidate actually different from something
we already have?"
```

That is its role.

# The revised Task Library architecture

I would now build it around **five responsibilities**.

```text
                     TASK LIBRARY
                          │
        ┌─────────────────┼──────────────────┐
        │                 │                  │
        ▼                 ▼                  ▼
 FAMILY REGISTRY    IDENTITY / INDEX   VALIDATION KNOWLEDGE
        │                 │                  │
        │                 │                  │

        │
        └─────────────────┼──────────────────┘

                          │
                          ▼
                  REPRODUCIBILITY
```

We do not need more than that.

## 1. Family Registry

This stores the canonical `TaskFamily`.

Something like:

```yaml
family_id: constrained_pick_place
version: 2.1.0

status: active

task_spec:

  objects:
    movable:
      requires:
        - graspable

    target:
      requires:
        - receptacle

    obstacle:
      requires:
        - collision_object

  initial_state:
    - reachable(robot, movable)
    - outside(movable, target)

  goal:
    - inside(movable, target)
    - stable(movable)

  skill_graph:
    - reach
    - grasp
    - lift
    - transport
    - align
    - place

  task_parameters:
    placement_tolerance:
      min: 0.005
      max: 0.050

    obstacle_count:
      min: 0
      max: 4

    transport_distance:
      min: 0.10
      max: 0.60

  environment_randomization:
    friction:
      min: 0.4
      max: 1.1
```

The TaskSpec remains relatively small.

We should **not** stuff validation results, Advisor performance, policy statistics, or experiment history into the TaskSpec itself.

# 2. Formal family identity

This is the most important change from the earlier Library.

Before registering a proposed family, we determine:

> Is this genuinely a new family or simply another part of an existing family's parameter space?

Family identity should be based predominantly on:

\[
F =
(
G,
S,
O,
C
)
\]

where:

- \(G\) = goal structure
- \(S\) = skill/dependency structure
- \(O\) = object-role structure
- \(C\) = structural constraints

For example:

```text
pick → place
tolerance = 5 cm
```

versus:

```text
pick → place
tolerance = 5 mm
```

should normally remain the same family.

The difference belongs in:

\[
\theta
\]

But:

```text
pick
→ route around obstacle
→ orient
→ insert
```

contains genuinely different structural requirements and may deserve its own family.

This prevents library fragmentation as the Generator starts producing thousands of candidates.

---

# 3. Validation becomes a parameter-space envelope

We should completely avoid:

```yaml
validated: true
```

because that is too coarse.

Instead:

```yaml
validation_envelope:

  robot:
    so101_v1

  compiler_version: 7
  validator_version: 4

  confirmed_valid:

    - obstacle_count: [0, 2]
      placement_tolerance: [0.010, 0.050]
      transport_distance: [0.10, 0.45]

  confirmed_invalid:

    - obstacle_count: [4, 5]
      corridor_width: [0.00, 0.06]

  unknown:
    ...
```

Now the Curriculum Sampler knows exactly where it can safely sample.

This turns validation from:

> Is family X valid?

into:

> Which parts of family X are known to produce valid SO-101 tasks?

That is much more useful for synthetic-data generation.

---

# 4. Separate semantic validity from SO-101 feasibility

This is critical for making the architecture extensible.

Consider:

```text
peg insertion
```

That might be a perfectly valid robotic task.

But perhaps:

```text
SO-101
+
our current gripper
+
current controller
```

cannot perform some versions.

The Library should therefore store:

```yaml
semantic_status:
  valid: true

compatibility:

  so101_v1:
    status: partial
    validation_envelope: ...

  franka_v1:
    status: compatible
    validation_envelope: ...
```

So:

\[
\text{Task validity}
\neq
\text{Robot feasibility}
\]

This prevents us from accidentally designing the entire task ontology around the limitations of SO-101.

For this project, SO-101 compatibility is what determines whether a family enters the **active synthetic-data curriculum**, but the underlying family can remain robot-independent.

---

# 5. Search and structural indexing

The Library must answer queries quickly.

For example, the Task Advisor produces:

```yaml
learn:
  capabilities:
    - precision_placement
    - sequencing
```

The Library should be able to return:

```text
precision_pick_place
retrieve_route_place
object_sort
constrained_rearrangement
...
```

Each family therefore needs indexes for:

```text
capabilities
goal structure
skill structure
object roles
task parameters
status
robot compatibility
```

And every family gets a normalized structural signature.

For example:

```yaml
structural_signature:

  goal:
    inside(movable,receptacle)

  skills:
    reach>grasp>transport>place

  object_roles:
    - movable
    - receptacle

  constraints:
    - collision_avoidance
```

The Generator's novelty checker can then retrieve the nearest structural matches rather than comparing a candidate against every family in the database.

That is enough initially.

I would **not introduce embeddings or vector databases yet**.

# Lifecycle

I would use this lifecycle:

```text
PROPOSED
    │
    ▼
STRUCTURALLY_ACCEPTED
    │
    ▼
VALIDATING
    │
    ├─────────► REJECTED_CONTEXTUALLY
    │
    ▼
VALID
    │
    ├─────────► ARCHIVED
    │
    ▼
ACTIVE
    │
    └─────────► DEPRECATED
```

There is an important distinction here:

### VALID

The task is legitimate.

### ACTIVE

The task is currently available to the SO-101 curriculum.

So we could have:

```text
valid family:
tool_manipulation

SO-101 active:
false
```

without throwing away that task knowledge.

# Rejections also need context

A rejection should never mean:

> This task is permanently bad.

Instead:

```yaml
rejection:

  reason:
    workspace_infeasible

  context:
    robot: so101_v1
    gripper: standard
    compiler_version: 7
    validator_version: 4
```

Later:

```text
new controller
new gripper
new robot
better planner
```

may make the same family viable.

So contextual rejection does not poison future exploration.

# Versioning

Each TaskFamily should use semantic-style versioning.

For example:

```text
2.3.1
```

with:

```text
PATCH
metadata/implementation change
task semantics unchanged

MINOR
compatible extension of task space

MAJOR
semantic meaning changed
```

Example:

```text
2.3.1 → 2.3.2
description fixed
```

versus:

```text
2.3.1 → 3.0.0
success predicate changed
```

A major change means historical Advisor results should not automatically transfer.

This protects experiment reproducibility.

# Provenance

Every generated family should tell us where it came from.

For example:

```yaml
provenance:

  source:
    composition

  parents:
    - retrieve_object
    - obstacle_transport

  generator_version: 8

  proposal_id:
    gen_28392
```

Other sources might be:

```text
human
mutation
composition
LLM proposal
```

This later allows us to answer interesting research questions like:

```text
Which generation mechanism produces the most
useful new capabilities?

Which produces mostly duplicates?

Which families transfer best?
```

Without provenance, that analysis becomes impossible.

This integration is especially clean.

## Final role of each major engine

The cleanest way to understand the complete platform is:

| Component | Question it answers |
|---|---|
| **Task Advisor** | What should the robot learn next? |
| **Task Library** | What reusable task knowledge do we already have? |
| **Task Generator** | What new task structures could fill our capability gaps? |
| **TaskSpec / DSL** | What exactly does this robotic task mean? |
| **Task Compiler** | How do we turn that meaning into an executable simulator environment? |
| **Task Validator** | Is this task feasible, and in which parameter regions? |
| **Curriculum Sampler** | Which family/region should we train from right now? |
| **Instance Generator** | Which exact \( \theta,\phi \) configuration should this episode use? |
| **Isaac Lab** | Execute the environment and generate experience. |
| **Evidence Engine** | What happened? |
| **Capability Model** | What can SO-101 actually do now? |

The Advisor implementation we designed already follows this evidence → capability → task-space → selection pattern rather than trying to infer capability directly from raw outcomes. Discussion Summary

### The Task Library's one-sentence mission

> **The Task Library is the durable knowledge layer that turns autonomous task discovery into a controlled, reusable, reproducible task space from which the platform can continuously generate useful SO-101 synthetic training data.**

I don't see a major architectural conflict remaining after these changes. The most important thing going forward is to keep the ownership boundaries above strict. If we do that, the Library can grow substantially without turning the Generator, Advisor, or training pipeline into one tightly coupled system.
